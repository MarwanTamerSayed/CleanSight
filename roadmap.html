💡 The Core Insight

Most tutorials skip the cleaning phase because "clean" is ambiguous — is this numeric column with "N/A" strings broken? Are three date formats in one column a bug or reality? Should duplicates be dropped? Forcing the agent to reason from a data profile instead of guessing is exactly the retrieval/reasoning skill real agentic systems need. That's why we added it.

Node-by-node breakdown

1️⃣ Load CSV + Profile Data

No LLM here. Compute a structured profile programmatically — much cheaper and more reliable than dumping a huge CSV into context:

  • dtypes per column, % missing, # unique values
  • sample of 5 rows
  • Flag suspicious columns: numeric-looking strings, inconsistent date formats, mixed-case categories (Yes/yes/YES), potential ID columns, outliers via IQR

The profile (not raw data) is what gets fed to the LLM downstream.

2️⃣ Plan Cleaning → 3️⃣ Generate Cleaning Code

The LLM reads the profile and outputs cleaning steps in plain English first ("strip whitespace in 'name'", "convert 'date' to datetime"). This separation makes debugging easy — you can log and inspect plans without reading code.

Then a second call converts the plan into pandas code, heavily constrained: give it exact column names + dtypes from the profile and instruct it to only use those names. This is your first line of defense against hallucinated columns.

4️⃣ Execute Cleaning

Run inside sandboxed exec() with a restricted namespace (only pandas/numpy available; no os, no network). Catch exceptions and capture them as strings for the critique step. Wrap with a timeout guard.

5️⃣ Critique Cleaning

Rule-based checks run before any LLM call:

  • Did execution throw an error? → fail, send error back
  • Still nulls in columns the plan claimed to fix? → fail
  • Row count collapsed to near-zero (over-aggressive dropna)? → fail
  • Do dtypes now match what was intended? → fail if not

Only if all rules pass, run one optional Gemini sanity check on a before/after sample: "does this look correctly cleaned? yes/no + why."

6️⃣ Plan Analysis

Same pattern as cleaning: Gemini reads the cleaned schema + the user's question and writes an English analysis plan before touching code. This step is what lets the agent answer "which region had the highest growth rate" instead of only "what is the average X".

7️⃣+8️⃣ Generate Code → Execute (analysis version)

Reuses the same sandbox as Day 1. Generated pandas code operates on the cleaned dataframe and must store its result in a known variable (e.g., result = ...) so execution can capture it deterministically.

9️⃣ Synthesize Final Answer

Validated result + original question → Gemini phrases a clean natural-language answer, optionally with a one-line "how I got this" explanation for transparency. If retries were exhausted: graceful fallback — "I couldn't confidently answer this; here's my best attempt and why."

03The Cleaning Phase — Deep Dive

Your addition, and conceptually the hardest part. Here's how each ambiguity gets resolved by the pipeline.

Why profiling comes first

Cleaning decisions must come from evidence, not vibes. The profiler produces facts the planner can reason over:

# profiler.py — pure pandas, zero LLM cost
def profile_dataframe(df: pd.DataFrame) -> dict:
    report = {}
    for col in df.columns:
        s = df[col]
        entry = {
            "dtype": str(s.dtype),
            "null_pct": round(s.isna().mean() * 100, 1),
            "n_unique": int(s.nunique()),
            "sample": s.dropna().astype(str).head(5).tolist(),
            "flags": [],
        }
        # numeric-looking but stored as object → dtype coercion candidate
        if s.dtype == object:
            coerced = pd.to_numeric(s.str.strip().replace({"": None}), errors="coerce")
            if coerced.notna().mean() > 0.9:
                entry["flags"].append("numeric_in_object_dtype")
            parsed = pd.to_datetime(s, errors="coerce", format="mixed")
            if parsed.notna().mean() > 0.9:
                entry["flags"].append("date_like_string")
        # mixed-case categoricals: Yes / yes / YES
        if s.dtype == object and s.nunique() < 50:
            lowered = set(s.dropna().astype(str).str.lower())
            if len(lowered) < s.nunique():
                entry["flags"].append("mixed_case_categorical")
        # potential ID column
        if s.nunique() == len(df):
            entry["flags"].append("possible_id_column")
        # IQR outliers (numeric only)
        if pd.api.types.is_numeric_dtype(s):
            q1, q3 = s.quantile([0.25, 0.75])
            iqr = q3 - q1
            n_out = ((s < q1 - 1.5*iqr) | (s > q3 + 1.5*iqr)).sum()
            if n_out:
                entry["flags"].append(f"{n_out}_iqr_outliers")
        report[col] = entry
    report["_meta"] = {"n_rows": len(df), "dup_rows": int(df.duplicated().sum())}
    return report

How ambiguities get decided

Messy situationProfile evidencePlanner decision
Numeric column with "N/A" stringsnumeric_in_object_dtypeCoerce to numeric; decide whether N/A → NaN or fill
Date column in 3 formatsdate_like_string + samples show formatsParse with pd.to_datetime(format="mixed")
Duplicate rowsdup_rows > 0; ID column flagged?If ID exists and dups share IDs → likely true dups, drop; else keep & note
Yes/yes/YESmixed_case_categoricalNormalize case
Weird extreme valuesN_iqr_outliersFlag, don't delete — outliers may be legitimate business data

🔑 Design rule

The cleaning critique verifies the outcome against the plan: if the plan said "fix nulls in 'age'", the checker re-runs df["age"].isna() after execution. Plans become machine-checkable contracts — that's what makes self-correction possible rather than hopeful.

04Critique Node Design — The Core of the Project

This is where the agent catches its own mistakes instead of you catching them. Design principle: cheapest checks first, escalate to LLM judgment only when rules pass.

L1
⚡ free · pre-execution Static column validation (AST walk)

Parse the generated code with Python's ast module, extract every attribute/subscript reference like df["colname"] or df.colname, and diff against the actual dataframe columns before running anything. Hallucinated columns die instantly without wasting an execution.

import ast, re

def find_column_refs(code: str, cols: set[str]) -> list[str]:
    tree = ast.parse(code)
    refs = set()
    for node in ast.walk(tree):
        # df["col"] pattern
        if isinstance(node, ast.Constant) and isinstance(node.value, str):
            refs.add(node.value)
        # df.col pattern
        if isinstance(node, ast.Attribute) and isinstance(node.value, ast.Name):
            if node.value.id == "df":
                refs.add(node.attr)
    return sorted(r for r in refs if r not in cols and not r.startswith("_"))

Tip: also do a fuzzy match — if "Region " was referenced but the column is "Region", suggest the strip fix directly in suggested_fix.

L2
⚡ free · post-execution Execution & emptiness checks

Did it error? Is the captured result None, an empty DataFrame, or an empty list/dict/Series? All fail automatically with the exception string fed back verbatim into the next generation attempt — error messages are the best repair context you have.

L3
⚡ free · post-execution Type-consistency check

Does the answer type match what the question implies? "How many…" should return a number — not a DataFrame dump. "Which…" should return a label/category, not an aggregate. A simple regex classifier on the question picks the expected shape; mismatch → fail with a targeted hint.

Question starts with…Expected result type
how many / how much / count / totalint | float
which / who / namestr (label)
average / mean / ratio / percentagefloat (sanity range check too!)
list / top / comparelist | Series | small DataFrame
L4
💸 ~1 Gemini call · last resort Gemini-as-judge (structured JSON)

Show Gemini the question + code + cleaned schema + result and ask it to verify logical consistency (percentage over 100%? negative count?). Force JSON output:

{
  "passes": false,
  "reason": "Result is revenue sum, but question asks for growth rate — needs year-over-year comparison.",
  "suggested_fix": "Group by 'region' and compute pct change between 'sales_2023' and 'sales_2024'."
}

The magic ingredient: suggested_fix is injected as extra context into the next generate_code call. That's what makes the retry loop actually improve instead of repeating the same mistake.

Guardrails regardless of layer

  • Max retries (3) on both loops, then graceful fallback answer
  • Sandboxed exec — restricted globals dict, no filesystem/network access
  • Timeouts on every execution (threading or signal.alarm-style guard) in case of infinite loops in generated code

05State Schema (Shared Between Subgraphs)

One TypedDict flows through every node. Fields are grouped so the cleaning graph owns the top half and analysis owns the bottom half.

from typing_extensions import TypedDict
import pandas as pd

class AgentState(TypedDict):
    # ── cleaning subgraph ──
    raw_df_path: str
    profile_report: dict          # dtypes, null%, flags, dup rows, samples
    cleaning_plan: list[str]      # ["strip whitespace in 'name'", "convert 'date' to datetime"]
    cleaning_code: str
    cleaned_df: pd.DataFrame
    cleaning_errors: list[str]
    cleaning_retries: int

    # ── analysis subgraph ──
    question: str
    analysis_plan: str
    generated_code: str
    execution_result: object
    execution_error: str | None
    critique_feedback: dict       # {"passes": bool, "reason": str, "suggested_fix": str}
    analysis_retries: int

    # ── output ──
    final_answer: str

08Gemini-Specific Tips

Practical guidance for getting reliable behavior out of Gemini in each node.

NodeModel choiceKey settings / technique
Plan cleaning / plan analysisgemini-2.0-flashUse JSON mode (response_mime_type="application/json") so plans parse reliably; temperature ≈ 0.2
Generate code (both phases)gemini-2.0-flash (pro if struggling)Inject the exact column list + dtypes; forbid imports beyond pandas/numpy; demand a single fenced block storing results in result
Gemini-as-judgegemini-2.0-flashForce JSON schema {passes, reason, suggested_fix}; include the cleaned schema, NOT raw data; temperature 0
Synthesize answergemini-2.0-flashGive question + validated result + plan summary; keep it short and honest about uncertainty

Cost control

  • Feed the profile (KBs), never the raw CSV (MBs) — this alone keeps most calls tiny
  • Rule layers L1–L3 catch ~80% of failures with zero token spend
  • Cap judge calls at 1 per retry cycle
  • Free tier is enough for development; flash models are cheap even at volume

Prompt skeleton for generate_code (the constraint-heavy one)

You are writing pandas code for a cleaned dataframe `df`.

AVAILABLE COLUMNS (use ONLY these, exact spelling):
{columns_with_dtypes_from_profile}

TASK PLAN:
{english_plan}

{IF_RETRY: A previous attempt failed.
Error/judge feedback: {error_or_suggested_fix}
Previous code:
{previous_code}}

RULES:
1. Import nothing except pandas (as pd) and numpy (as np).
2. Store the final answer in a variable named `result`.
3. No file/network/system operations.
4. If a column seems missing, STOP and explain in a comment — never guess names.

Return only the code.

Cleaning silently corrupting analysisPlan-vs-outcome contracts checked mechanically; Day 1 stability gate before Day 2

  • Ask a natural-language question → validated answer with visible reasoning trail
